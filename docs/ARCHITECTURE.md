# Architecture

_Phase 1. This document describes what is implemented, not aspirations._

## System shape

```
PUBLIC SOURCES (Phase 1: demo_seed connector only)
      │  SourceConnector.collect()
      ▼
raw_items  ── immutable connector-native payloads, idempotent on
      │       (platform, external_id, data_origin)
      │  SourceConnector.normalize() → per-platform normalizers
      ▼
mentions  ── the canonical intelligence object (one row per public item)
      │
      │  INTELLIGENCE PIPELINE (each stage records processing_events)
      ├─ relevance gate      deterministic ontology matching (free, first)
      ├─ enrichment          Zod-validated structured extraction
      ├─ deduplication       exact hash + near (bigram/unigram Jaccard)
      ├─ narrative stage     rule-based assignment + aggregation + snapshot
      └─ finding stage       explainable NOW findings + evidence links
      ▼
UI (Next.js server components) — reads precomputed aggregates only
```

## Stack

- **Next.js 16** (App Router, TypeScript strict), server components only so far.
- **Drizzle ORM** + SQL migrations (`src/db/migrations`, generated by
  drizzle-kit).
- **Postgres via two interchangeable drivers**: node-postgres when
  `DATABASE_URL` is set; embedded **PGlite** (WASM Postgres, `.data/pglite`)
  otherwise. Same schema, same migrations, same Drizzle API — development and
  tests need zero credentials. Tests use in-memory PGlite.
- **Zod** for the enrichment contract; **Vercel AI SDK** for the (currently
  inactive) LLM enricher.

## Boundaries that matter

### Connectors (`src/ingestion/connectors`)

Every source implements:

```ts
interface SourceConnector {
  key: string;
  platform: Platform;
  collect(query: CollectionQuery): Promise<RawSourceItem[]>;
  normalize(item: RawSourceItem): Promise<NormalizedMention>;
}
```

The pipeline never sees connector-native payload shapes. Normalizers
(`src/ingestion/normalization`) are keyed by platform and are the production
code paths: the demo corpus payloads deliberately mimic the platform APIs
(YouTube video resource, X post, news article, official release, web page) so
a live connector swaps in without touching normalization, intelligence, or UI.

### Job layer (`src/ingestion/jobs`)

Jobs are plain async functions over `{ db, log, enricher? }`. Nothing imports
a scheduler. Phase 1 drives them from a CLI script (`npm run pipeline`);
Vercel Cron, Trigger.dev, Temporal, or queue workers can call `runJob()`
later without any change to collectors or intelligence stages.

### Intelligence stages (`src/intelligence/*`)

Each stage is an independent module with a `runXStage(db, …)` entry point,
selecting work by mention status:

`normalized → (rejected | enriched) → (duplicate | narrative_assigned)`

Stages are idempotent and re-runnable; re-processing already-processed rows is
a no-op (verified by tests).

## Identifiers and idempotency

- Application-generated UUID v4 primary keys.
- Natural-key uniqueness: `(platform, external_id, data_origin)` on raw items
  and mentions; `(platform, natural_key, data_origin)` on authors;
  `(key, data_origin)` on narratives; `(narrative_id, mention_id)` and
  `(finding_id, mention_id)` on link tables.
- Raw payloads are never updated after insert.
- Findings are regenerated per pipeline run: the previous active set is marked
  `superseded`, so the active set is always internally consistent.

## data_origin

Every data-bearing row carries `data_origin: live | verified_snapshot |
demo_seed`. Narratives and findings inherit it from their evidence. The UI
derives its environment ribbon from the origins actually present in the
database — seeded development data can never masquerade as live intelligence.

## Database driver notes

- PGlite requires `serverExternalPackages: ["@electric-sql/pglite"]` in
  `next.config.ts` (its WASM loading breaks under bundling).
- PGlite is single-connection: the dev server and the pipeline script must
  not hold the same data directory simultaneously for writes. In practice:
  run `npm run pipeline`, then `npm run dev`. (A real Postgres has no such
  constraint; CI/tests use in-memory instances.)

## Known Phase 1 limitations

- Narrative assignment is rule-based (`assigned_by = "rule"`); the schema and
  stage interface already carry `assigned_by = "model"` for future clustering.
- The heuristic enricher cannot translate or summarise; translation of demo
  content is corpus-authored and labelled `seed_authored`. The LLM enricher
  (same Zod contract) activates when `AI_GATEWAY_API_KEY` is set.
- Near-duplicate detection is O(n²) pairwise within a pipeline run — fine at
  Phase 1 volume; the module boundary allows MinHash/embeddings later.
- No trend/velocity computation yet (single snapshot per run exists as the
  raw material for it).
